研究判断ではなく、
再現可能な実装を支える。

Claude Codeの役割は、研究者が決めた問い・データ・評価基準を、追跡可能な解析コードへ落とすこと。 BiG Lab資料にある活用方針を、実装の順番と安全境界にまとめました。

ローカルのインターン資料に記載されたClaude Code経験・AI支援方針の整理です。製品仕様や正式なラボ方針を示すものではありません。

データ利用許可が先

患者情報、未公開データ、ラボ承認前のファイルをClaude Codeや外部AIへ入力しないでください。使用環境、保存、ログ、外部送信、公開範囲を研究室へ確認してから始めます。

Core role

問いを決めず、決まった問いを実装する。

Claude Codeは、研究者の代わりに生物学的意味、sample除外、臨床的主張を確定するものではありません。入力、処理、出力、検証をコードとして明示する補助者です。

Researcher owns the claim. Code makes the path traceable.

研究者が問い、experimental unit、primary metric、許可範囲を決め、Claude Codeがloader、検証、metric、test、reportへ落とし込みます。

Six useful jobs

研究repoで任せる6つの仕事。

最初から大規模なAIモデルを作らず、測定・品質管理・再実行性を固めます。

01 / STRUCTURE

repoを整える

raw、processed、src、tests、config、reportsを分け、データをGitへ入れない構造を作る。

02 / VALIDATE

入力を検証する

sample ID、run、batch、単位、pixel size、欠損、重複を読み込み時に確認する。

03 / IMPLEMENT

測定を実装する

校正、segmentation、registration、metric計算を小さな関数へ分離する。

04 / TEST

不変条件をテスト

既知寸法、同一入力、単位変換、空データ、失敗画像で期待結果を確認する。

05 / REPORT

QCを可視化する

数値だけでなくoverlay、偏差マップ、QC flag、method versionを一緒に出す。

06 / DOCUMENT

方法と限界を残す

README、再実行手順、入力条件、失敗条件、言えること／言えないことを記録する。

Implementation flow

コードを書く前から、レビュー後まで。

人間がproject charterを承認

研究上の問い、入力、experimental unit、primary metric、範囲外、データ利用を一文で固定します。

Claude Codeへ制約と完了条件を渡す

repo規約、read-onlyのraw、出力先、許可package、期待するtestとartifactを明記します。

まずloaderと検証を作る

解析より前にID、階層、単位、欠損、校正情報を検証し、壊れた入力で止まるようにします。

小さなbaselineとtestを実装

少数の承認済みsampleで測定し、既知値・手動reference・失敗例をtestへ含めます。

差分と実行結果を人間が確認

コード変更、overlay、metric表、警告、未解決事項を研究者へ提示します。

固定versionから成果物を再生成

configとmethod versionを残し、別の人が同じ入力から同じ図とCSVを作れるか確認します。

DONE → CODE + TEST + OVERLAY + METHOD + LIMITATIONS

Request templates

依頼には、判断済み事項を書く。

下の文面は下書きです。実際のpath、データ分類、metric、ラボ規約に置き換えます。

この研究repoに、src / tests / config / reports / notebooksを作ってください。data/rawはread-onlyとして扱い、Git対象外を維持してください。まず既存構成と規約を確認し、変更計画を示してください。入力を変更せず、成果物はreports以下へ出します。完了条件は、READMEの再実行手順と最小testが通ることです。
解析はまだ行わず、承認済みsample tableのschemaだけを監査してください。study / experiment / print_run / bioink_batch / construct / timepoint / fieldの階層、単位、欠損、重複、参照切れを確認し、問題一覧とdata dictionary案を出してください。科学的な除外判断はせず、確認が必要な項目として返してください。
承認済みのprimary metricを1つだけ実装してください。単位と校正を明示し、既知寸法、同一入力の再実行、空入力、範囲外値のtestを追加してください。全sampleにoverlayまたはQC flagを保存し、parameterをsampleごとに後付け調整しないでください。未確定の研究判断はTODOとして止めてください。
コード差分、test結果、各sampleのQC、手動referenceとの差、failure modeを研究者レビュー用に1ページで要約してください。「この結果から言えること」「言えないこと」「研究者の確認が必要なこと」を分け、元sampleとmethod versionへ追跡できるようにしてください。新しい科学的主張は追加しないでください。

Guardrails

AIへ渡さない判断を先に決める。

Raw dataを固定

  • 入力を上書きしない
  • 派生データを別folderへ
  • sample IDで出力へ追跡

未公開情報を守る

  • 外部AI利用を事前確認
  • 個人GitHub・cloudへ置かない
  • ログと保存場所を確認

研究判断を戻す

  • 除外を自動確定しない
  • 生物学的意味を断定しない
  • 臨床的主張を作らない

失敗を成果物に含める

  • 代表画像だけを選ばない
  • overlayとQC flagを全件保存
  • 適用範囲とfailure modeを明記

Four-week integration

QC pilotでのClaude Codeの位置。

WEEK 1

定義をコード化

  • charterとdata dictionaryを読む
  • repo構造と入力検証
  • 未確定事項を質問として返す
WEEK 2

baseline実装

  • loader、校正、metric
  • overlayとQC flag
  • 既知値のtest
WEEK 3

reference比較

  • 手動値との差を計算
  • failure modeを分類
  • 個別調整を減らす
WEEK 4

再実行可能に渡す

  • 固定configで全再生成
  • methodと限界を文書化
  • 研究者レビューへ提出
